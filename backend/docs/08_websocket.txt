================================================================================
SOCKET.IO - COMUNICACAO EM TEMPO REAL
================================================================================

O sistema atual usa Socket.IO sobre o mesmo backend HTTP.
Nao existe namespace publico documentado em `/ws/*`.

Conexao padrao:
- frontend local: `http://localhost:3001`
- via proxy do frontend em producao/docker: mesma origem do painel

-------------------------------------------------------------------------------
1. AUTENTICACAO
-------------------------------------------------------------------------------

A conexao exige token JWT.

Exemplo:

```ts
const socket = io('http://localhost:3001', {
  transports: ['websocket'],
  auth: { token: localStorage.getItem('auth_token') }
})
```

O backend tambem aceita token no header `Authorization: Bearer <token>`.

Se o token faltar ou estiver invalido:
- a conexao e rejeitada
- o cliente recebe erro de autenticacao

-------------------------------------------------------------------------------
2. EVENTOS CLIENTE -> SERVIDOR
-------------------------------------------------------------------------------

Assinaturas gerais:
- `subscribe:dashboard`
- `subscribe:orders`
- `subscribe:logs`
- `subscribe:traces`

Assinatura de treinamento:
- `subscribe:training`
  - payload: `sessionId` em string

Cancelamento:
- `unsubscribe:dashboard`
- `unsubscribe:orders`
- `unsubscribe:logs`
- `unsubscribe:traces`
- `unsubscribe:training`
  - payload: `sessionId`

-------------------------------------------------------------------------------
3. EVENTOS SERVIDOR -> CLIENTE
-------------------------------------------------------------------------------

Eventos de conexao:
- `connected`
- `error`

Eventos operacionais:
- `dashboard:update`
- `order:created`
- `order:updated`
- `log:new`
- `trace:new`
- `training:status`
- `training:metrics`
- `training:log`

-------------------------------------------------------------------------------
4. FORMATOS IMPORTANTES
-------------------------------------------------------------------------------

### 4.1 connected

```json
{
  "message": "connected",
  "userId": "user_123"
}
```

### 4.2 dashboard:update

Hoje esse evento funciona como gatilho de sincronizacao, nao como snapshot completo.

```json
{
  "scope": "portfolio",
  "reason": "order_executed",
  "updatedAt": "2026-04-26T10:00:00.000Z",
  "botId": "bot1"
}
```

`scope`:
- `portfolio`
- `bots`

Uso no frontend:
- invalidar/refetch das queries relacionadas

### 4.3 order:created / order:updated

Payload:
- objeto de ordem/transacao relevante para a tela de transacoes e para o dashboard

### 4.4 log:new / trace:new

Payload:
- entrada normalizada de log ou trace

Observacao:
- `subscribe:logs` inscreve tanto nos logs do proprio usuario quanto nos logs de sistema liberados para a UI

### 4.5 training:status / training:metrics / training:log

Payloads:

```json
{ "sessionId": "session_1", "status": "running" }
```

```json
{ "sessionId": "session_1", "metrics": { "epoch": 10, "trainLoss": 0.02 } }
```

```json
{ "sessionId": "session_1", "log": { "level": "INFO", "message": "checkpoint salvo" } }
```

-------------------------------------------------------------------------------
5. FLUXO RECOMENDADO NO FRONTEND
-------------------------------------------------------------------------------

1. abrir conexao com token
2. escutar `connected`
3. emitir:
   - `subscribe:dashboard`
   - `subscribe:orders`
   - `subscribe:logs`
   - `subscribe:traces`
4. quando entrar em uma tela de treino, emitir `subscribe:training` com `sessionId`
5. usar os eventos para sincronizar React Query e atualizar a interface
6. ao sair, cancelar inscricoes especificas ou fechar o socket

-------------------------------------------------------------------------------
6. SALAS INTERNAS USADAS PELO BACKEND
-------------------------------------------------------------------------------

O backend organiza a distribuicao por salas privadas:
- `user:{userId}`
- `user:{userId}:dashboard`
- `user:{userId}:orders`
- `user:{userId}:logs`
- `user:{userId}:traces`
- `user:{userId}:training:{sessionId}`
- `system:logs`

Isso garante que:
- eventos de dashboard, ordens e traces sejam isolados por usuario
- logs de sistema possam ser propagados para os clientes autorizados que escutam logs
- treinamento seja filtrado por sessao e por dono

-------------------------------------------------------------------------------
7. OBSERVACOES DE MANUTENCAO
-------------------------------------------------------------------------------

- o contrato realtime atual e Socket.IO, nao WebSocket bruto com `/ws/dashboard`
- `subscribe:training` recebe `sessionId` como payload; nao existe evento nomeado `subscribe:training:{id}`
- o frontend atual usa os eventos como gatilho de sincronizacao, nao como unica fonte de dados
