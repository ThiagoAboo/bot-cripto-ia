-------------------------------------------------------------------------------
2. API: PUT /api/configurations
-------------------------------------------------------------------------------

Descrição: Salva todas as configurações do usuário

HEADERS:
  Authorization: Bearer {token}
  Content-Type: application/json

REQUEST BODY: (mesma estrutura do GET)

RESPONSE (200 - Sucesso):
{
  "success": true
}

RESPONSE (400 - Validação):
{
  "success": false,
  "error": "stopLossPercent deve ser entre 0 e 50"
}

TABELAS ENVOLVIDAS:
- Configuration (cria ou atualiza)

CAMPOS ATUALIZADOS:
- Todos os campos da tabela Configuration

VALIDAÇÕES:

| Campo                    | Validação                                    |
|--------------------------|----------------------------------------------|
| stopLossPercent          | 0 < valor ≤ 50                               |
| takeProfitPercent        | 0 < valor ≤ 100                              |
| leverage                 | valor fixo = 1 no runtime spot atual         |
| maxTradeAmount           | > 0                                          |
| discountUsdtPercent      | 0 ≤ valor ≤ 1                                |
| discountBnbPercent       | 0 ≤ valor ≤ 1                                |
| minBnbBalance            | ≥ 0                                          |
| useBnbForFees            | boolean                                      |
| reserveBnbForFeesEnabled | boolean                                      |
| slippagePercent          | 0 ≤ valor ≤ 5                                |
| allowedPairs             | Array de strings (pares válidos)             |
| pairDiscovery            | Estrutura válida com fontes, limites e exclusões |
| strategies               | Array com estrutura válida                   |

REGRAS FUNCIONAIS ADICIONAIS:
- Se useBnbForFees = true, o sistema deve priorizar taxa em BNB quando houver saldo disponível
- minBnbBalance representa o saldo mínimo de BNB que deve permanecer livre para pagamento de taxas
- reserveBnbForFeesEnabled = true impede consumo do saldo reservado de BNB por trades comuns
- pairDiscovery controla descoberta automática de moedas a partir de sinais externos/sociais
- autoAddToAllowedPairs/autoRemoveFromAllowedPairs só podem atuar dentro de maxPairs e respeitando excludedAssets

3. API: POST /api/configurations/test-connection
-------------------------------------------------------------------------------

Descrição: Testa as credenciais da API com a exchange

HEADERS:
  Authorization: Bearer {token}
  Content-Type: application/json

REQUEST BODY:
{
  "exchange": "binance",
  "apiKey": "xxxxx",
  "secretKey": "xxxxx"
}

RESPONSE (200 - Sucesso):
{
  "success": true,
  "message": "Conexão estabelecida com sucesso!"
}

RESPONSE (401 - Falha):
{
  "success": false,
  "message": "Chaves de API inválidas"
}

TABELAS ENVOLVIDAS:
- Nenhuma (apenas comunicação com exchange)

FLUXO:
1. Tentar fazer uma chamada autenticada à exchange (ex: GET /api/v3/account)
2. Se sucesso, retornar true
3. Se falha, retornar false com mensagem de erro

4.3 API: POST /api/configurations/backup/restore
-------------------------------------------------------------------------------

Descrição: Restaura um snapshot operacional completo para o usuário autenticado

HEADERS:
  Authorization: Bearer {token}
  Content-Type: application/json

REQUEST BODY:
{
  "snapshot": {
    "snapshotType": "bot-crypto-ia-user-backup",
    "formatVersion": 1,
    "...": "conteúdo exportado anteriormente"
  },
  "preserveCurrentApiKeys": true
}

RESPONSE (200 - Sucesso):
{
  "success": true,
  "data": {
    "restoredAt": "2026-04-15T11:30:00.000Z",
    "summary": "Backup restaurado com sucesso. 57 registros recriados. 5 arquivos restaurados. As chaves externas atuais foram preservadas.",
    "restoredRecords": {
      "balances": 2,
      "transactions": 25,
      "trainingSessions": 4
    },
    "restoredFiles": {
      "modelFiles": 3,
      "uploadFiles": 1,
      "checkpointFiles": 2
    },
    "preservedApiKeys": true,
    "configuration": {
      "...": "configuração já refrescada no contrato do frontend"
    }
  }
}

REGRAS FUNCIONAIS:
- A restauração limpa os dados atuais do usuário antes de recriar o snapshot
- As chaves externas atuais podem ser preservadas com preserveCurrentApiKeys = true
- IDs internos são remapeados para evitar colisão entre ambientes
- Referências entre bots, sessões, decisões, transações e artefatos são reescritas
- Arquivos de treino, upload e checkpoint são restaurados junto com os registros
- templateId dos bots é resolvido preferencialmente por BotTemplate.slug

OBSERVAÇÃO OPERACIONAL:
- O backend aceita payload JSON maior para suportar snapshots com artefatos serializados
- O frontend deve preferir esse fluxo para backup antes de resets destrutivos
- Manter governança via reviewRequired, limites e lista de exclusão
- managedPairs identifica quais pares foram adicionados pela curadoria automática e podem ser removidos depois sem afetar pares manuais
- autoSyncIntervalMinutes define a frequência mínima da curadoria automática em minutos
- lastSyncAt/lastAppliedAt/lastSyncStatus/lastSyncSummary registram o último ciclo automático executado

5. API: POST /api/configurations/reset
-------------------------------------------------------------------------------

Descrição: Executa limpezas seletivas para restaurar grupos de dados sem reinstalar o sistema

HEADERS:
  Authorization: Bearer {token}
  Content-Type: application/json

REQUEST BODY:
{
  "scope": "paper"
}

SCOPES SUPORTADOS:
- `logs_traces`: remove logs e traces
- `cash`: remove saldos e histórico de saldo
- `transactions`: remove ordens e transações
- `trainings`: remove sessões de treinamento e artefatos associados
- `paper`: remove ordens, decisões, saldos e histórico de saldo; depois recria o capital inicial do paper
- `bots_runtime`: limpa decisões avaliadas e reseta o estado operacional dos bots do usuário
- `all_except_configurations`: remove todos os dados operacionais do usuário, mantendo a tabela `Configuration`
- `configurations`: volta as configurações ao padrão inicial, preservando `exchange`, `apiKey` e `secretKey`
- `all`: combina todas as limpezas, restaura configurações padrão e recria o paper inicial

RESPONSE (200 - Sucesso):
{
  "success": true,
  "data": {
    "scope": "paper",
    "label": "Limpar paper",
    "summary": "Limpar paper executado com sucesso. 28 registros afetados. Paper restaurado com 10000 USDT.",
    "executedAt": "2026-04-14T14:00:00.000Z",
    "deletedRecords": {
      "logs": 0,
      "traces": 0,
      "balances": 3,
      "balanceHistory": 12,
      "transactions": 9,
      "trainingSessions": 0,
      "botDecisions": 4,
      "botsRuntimeResets": 2,
      "userBots": 0,
      "configurations": 0
    },
    "deletedFiles": {
      "modelFiles": 0,
      "uploadFiles": 0,
      "checkpointFiles": 0
    },
    "preservedApiKeys": false,
    "paperBalance": {
      "currency": "USDT",
      "amount": 10000
    },
    "configuration": {
      "...": "mesmo contrato do GET /api/configurations"
    }
  }
}

REGRAS FUNCIONAIS:
- `configurations` e `all` preservam as chaves externas e a exchange suportada (`binance`)
- `trainings`, `all_except_configurations` e `all` também removem artefatos de disco:
  - modelos salvos
  - uploads CSV
  - checkpoints
- `paper` recria a carteira local usando:
  - `PAPER_RESET_CURRENCY` (padrão `USDT`)
  - `PAPER_RESET_INITIAL_CAPITAL` (padrão `10000`)
- `all_except_configurations` remove bots materializados do usuário, mas mantém o catálogo global seedado (`BotTemplate` e bots globais)
- `bots_runtime` é uma limpeza extra pertinente para zerar o placar de `paperReadiness` sem apagar modelos ou configurações
- `transactions` é uma limpeza extra pertinente para reiniciar apenas o histórico operacional

4.4 API: POST /api/configurations/pair-discovery/run
-------------------------------------------------------------------------------

Descrição: Executa imediatamente um ciclo da curadoria automática usando a configuração persistida do usuário

HEADERS:
  Authorization: Bearer {token}

RESPONSE (200 - Sucesso):
{
  "success": true,
  "data": {
    "userId": "user-1",
    "applied": true,
    "previewRequired": false,
    "status": "applied",
    "summary": "1 adições e 0 remoções sugeridas",
    "preview": {
      "nextAllowedPairs": ["BTC/USDT", "DOGE/USDT"],
      "managedPairs": ["DOGE/USDT"]
    },
    "runner": {
      "running": true,
      "lastCycleAt": "2026-04-13T12:00:00.000Z"
    },
    "configuration": {
      "botParameters": {
        "pairDiscovery": {
          "lastSyncStatus": "applied"
        }
      }
    }
  }
}

REGRAS:
- Quando reviewRequired = true, o ciclo atualiza preview/metadata mas não altera allowedPairs automaticamente
- Quando reviewRequired = false, o ciclo pode aplicar allowedPairs e managedPairs diretamente
- O runner automático executa o mesmo fluxo de forma periódica quando autoDiscoveryEnabled = true

-------------------------------------------------------------------------------
4.4 API: POST /api/configurations/pair-discovery/apply
-------------------------------------------------------------------------------

Descrição: Aplica a curadoria automática no allowedPairs e atualiza managedPairs

REGRAS:
- Se reviewRequired = true e force != true, retorna apenas requiresConfirmation = true
- Quando aplicado, salva nextAllowedPairs em allowedPairs
- managedPairs persiste apenas pares adicionados automaticamente
- Nunca remove pares manuais
- Nunca remove BNB quando a reserva para taxas estiver habilitada

stopLossPercent          | Float   | Sim   | Stop-loss percentual

discountUsdtPercent      | Float   | Sim   | Desconto USDT
discountBnbPercent       | Float   | Sim   | Desconto BNB
minBnbBalance            | Float   | Sim   | Saldo mínimo BNB
mode                     | String  | Sim   | spot
orderType                | String  | Sim   | market/limit
slippagePercent          | Float   | Sim   | Slippage percentual
strategies               | String  | Sim   | JSON array
createdAt                | DateTime| Sim   | Data criação
updatedAt                | DateTime| Sim   | Data atualização

OBSERVAÇÃO DE EVOLUÇÃO:
- pairDiscovery pode evoluir para campo persistido dedicado
- fees e allowedPairs já existem persistidos; pairDiscovery representa a política futura de curadoria automática
- o runtime atual é `spot-only` e `binance-only`; valores legados diferentes de
  `spot`, `binance` ou `leverage = 1` devem ser normalizados na leitura e
  rejeitados em novas gravações
